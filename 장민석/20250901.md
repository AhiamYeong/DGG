# 클라우드 빅데이터 파이프라인 요약 (버스/지하철 승·하차 데이터)

> 목적: **덜 피로한 경로 추천**을 위해 정류장×시간대 집계 데이터를 클라우드에서 가공/활용하기

---

## 1) Hadoop vs Spark (핵심 차이)

| 구분    | **Hadoop (HDFS + MapReduce)** | **Spark (범용 분산 엔진)**                       |
| ----- | ----------------------------- | ------------------------------------------ |
| 처리 모델 | 디스크 중심 단계적 Map→Reduce         | **메모리 중심** DAG 실행 (반복/대화형에 유리)             |
| 속도/반복 | 반복 작업에 느림                     | 반복 ETL·SQL·ML에 빠름                          |
| 저장 연계 | **HDFS** 중심                   | HDFS, **S3 같은 오브젝트 스토리지** 직접 접근            |
| 사용 방식 | MapReduce, Hive 등             | **Spark SQL**, DataFrame, MLlib, Streaming |
| 운영    | 클러스터/버전/자원 직접 관리              | YARN/K8s/Standalone/Serverless 등 유연        |
| 권장 용도 | 레거시 배치/HDFS 중심 환경             | **현대적 ETL/SQL/ML/스트리밍** 전반                 |

**요약:** 신규·포폴 기준 **Spark 우선**(S3와 궁합, 생산성, 생태계).

---

## 2) 왜 클라우드에 올리나?

* **확장/탄력**: 필요할 때만 리소스 사용(서버리스/오토스케일) → 비용 효율
* **운영 부담↓**: 설치·패치·모니터링을 제공사가 대행(매니지드)
* **통합 생태계**: 저장–카탈로그–SQL–워크플로–시각화를 한 곳에서
* **데이터 인접성**: 같은 리전 서비스 간 네트워크 지연/데이터 이동 비용↓

> 유의: 보안(암호화/권한), 비용(스캔/전송량), 지역 법규 준수.

## 3) “커스텀” vs “AWS **매니지드**” & 선택 기준

### 용어

* **커스텀(직접 구축)**: EC2에 Hadoop/Spark **직접 설치/운영**
* **AWS 매니지드**: 설치·확장·장애대응을 **AWS가 관리**
  (예: **EMR/EMR Serverless**, **Glue**, **Athena**, **Redshift**, **Databricks on AWS**)

### 비교표

| 항목       | **커스텀(직접 구축)**      | **AWS 매니지드**        |
| -------- | ------------------- | ------------------- |
| 시작 속도    | 느림(설치/튜닝 필요)        | **빠름**(콘솔 몇 번)      |
| 운영 부담    | **높음**(장애/업그레이드 직접) | **낮음**(자동 확장/운영)    |
| 비용 구조    | 인스턴스 상주시 비용↑ 위험     | **사용량 기반**(서버리스·스팟) |
| 커스터마이징   | **자유도↑**            | 일부 제약(대신 표준화/안정성)   |
| 포폴/실무 적합 | 인프라 깊이 어필           | **실무 친화·생산성 어필**    |

### 선택 가이드

* **빠른 PoC/포폴·운영 여력 적음** → **매니지드(권장)**
* 특별한 네트워크/튜닝/폐쇄망 요구 → 커스텀
* 우리 상황(백엔드+클라우드 친화, 데이터 GB급) → **EMR Serverless + S3 + Glue + Athena**가 최적

## 4) 클라우드에 올리면 **어떻게 쓰나?** (사용 흐름)

```
[로컬/외부] 
   └─ 업로드 ─▶  [S3 Raw] 
                    └─(Spark/EMR Serverless ETL)─▶ [S3 Curated(Parquet, 파티션)]
                                                         └─(Glue)─▶ [Data Catalog]
                                                                     └─(Athena)─▶ SQL 분석/검증
                                                                     └─(API Gateway+Lambda)─▶ 추천 API
                                                                     └─(QuickSight/Metabase)─▶ 대시보드
```

* **S3 Raw**: 원본 CSV 보관
* **EMR Serverless(Spark)**: wide→long 변환, 일평균/혼잡 지표 산출
* **S3 Curated**: **Parquet + 파티션(ym/hour)** 저장 → 속도/비용 최적
* **Glue**: 스키마 카탈로그 자동화
* **Athena**: S3 데이터를 **서버리스 SQL**로 즉석 분석
* **API/대시보드**: 추천 결과 제공/시각화

## 5) **데이터를 클라우드에 어떻게 올리고 정리하나?** (실행 가이드)

### 5.1 S3 버킷·경로 (예시 네이밍)

* 버킷:

  * `transit-raw-<id>` / `transit-curated-<id>` / `transit-code-<id>` / `transit-logs-<id>`
* 공통 설정: **Block Public Access ON**, **SSE-S3 암호화 ON**, 리전 통일(서울)
* 경로 구조:

```
s3://transit-raw-<id>/bus_monthly/2025-05.csv           # 원본(CP949)
s3://transit-code-<id>/bus_wide_to_long.py               # Spark 스크립트
s3://transit-curated-<id>/bus_hourly/ym=YYYYMM/hour=HH/  # 결과 Parquet 파티션
```

### 5.2 변환(월별 wide → 시간대 long → Parquet)

* **컬럼 예시(원본)**: 사용년월, 노선ID/번호/명, 표준정류장ID, ARS, 역명, `00~23시 승차/하차 총승객수`, 등록일자
* **정규화 타깃 스키마(v1)**

  * `mode('bus')`, `ym(YYYYMM)`, `hour(0-23)`
  * `line_id, line_no, line_name`
  * `station_id, ars_id, station_name`
  * `in_cnt_m, out_cnt_m, total_flow_m, days_in_month`
  * `in_cnt_d, out_cnt_d, total_flow_d`, `reg_dt`
* **절차**

  1. S3 **Raw**에 CSV 업로드
  2. **EMR Serverless**에서 Spark 스크립트 실행(입·출력 경로만 전달)
  3. **S3 Curated**에 Parquet 저장(**파티션**: `ym/hour`)
  4. **Glue Crawler**로 카탈로그 등록 → **Athena**에서 SQL 확인

> 스크립트 인자(스파크 프로퍼티 예):
> `spark.app.input = s3://transit-raw-…/bus_monthly/`
> `spark.app.output = s3://transit-curated-…/bus_hourly/`

### 5.3 카탈로그 & SQL 확인(Athena)

```sql
-- 퇴근(18시)·출근(8시) 상위 정류장
SELECT ym, hour, station_name, line_no, AVG(total_flow_d) AS avg_flow
FROM transit.bus_hourly
WHERE hour IN (8,18)
GROUP BY ym, hour, station_name, line_no
ORDER BY avg_flow DESC
LIMIT 20;
```

### 5.4 (선택) 비용/거버넌스 팁

* \*\*파티셔닝(ym/hour)\*\*으로 스캔 범위 축소 → Athena 비용↓
* **예산 알림**(Budgets), **접근 로깅**(S3/CloudTrail) 활성화
* 원본/정제 버킷 분리, 스키마 버전 관리(폴더/테이블)
