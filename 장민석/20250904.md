## 1) 정규화 (1NF → 2NF → 3NF)

### 개념

1NF: 컬럼은 원자값만(리스트/CSV 금지).

2NF: 복합 PK일 때, PK 일부에만 의존하는 컬럼 분리.

3NF: a → b => b → c (추이적 종속) 제거. 마스터로 빼기.

### 예시

-- 잘못(1NF 위반): 출발지 문자열+참조 중복 보유
participant(id, plan_id, user_id, start_place_id, start_point VARCHAR(50))

-- 수정: start_point 제거, 참조만 유지
participant(id PK, plan_id FK, user_id FK, start_place_id FK, ...)


### 예외/트레이드오프

보고서용 숫자(합계/평균 등)는 즉시값 저장 대신 계산이 원칙.

다만 실시간 SLA가 빡세면 “집계 테이블”로 분리(반정규화 섹션 참고).

### 주의점

“name1, name2, name3” 같은 반복 컬럼은 무조건 분리.

코드값은 ENUM 몇 개가 끝이면 OK, 확장/다국어면 코드 마스터로.

### Q&A

Q: JSON 컬럼에 리스트 넣으면 1NF 위반?
A: 원칙적으론 위반. 다만 “스냅샷/로그”같은 비핵심 질의는 예외 허용(인덱싱 대상 아님).

Q: 정규화하면 JOIN 늘어서 느려지지 않나?
A: 핵심 쿼리에 맞춘 인덱싱을 먼저 하고, 부족할 때만 반정규화.

## 2) 반정규화 (언제, 어떻게)

### 개념

조회 ≫ 쓰기이고, 지연이 체감되며, 일관성 제어가 가능할 때만 중복/집계 저장 허용.

### 예시

-- 카운터 캐시(참가자 수)
ALTER TABLE meeting ADD participant_count INT NOT NULL DEFAULT 0;

-- 업데이트 규칙(예): 참가/탈퇴 트랜잭션 내 +1/-1

-- 스냅샷(경로 실행 당시 혼잡/시간)
route_history(id PK, user_id, route_id, started_at, snapshot_json JSON)


### 예외/트레이드오프

조기 최적화로 컬럼 난발 금지. 먼저 실행계획/지표로 병목 확인.

### 주의점

중복/집계는 업데이트 경로를 문서화(트리거/배치/서비스 계층).

원본 로그는 반드시 유지(추적/리커버리용).

### Q&A

Q: 카운터를 쿼리로 매번 세면 안 되나?
A: 트래픽/지연에 따라 가능. 핫한 화면이면 캐시/카운터가 유리.

Q: 스냅샷 JSON에 인덱스?
A: 핵심 필터 키는 정규 컬럼로 두고, JSON은 조회 전용/원본 기록으로.

## 3) 키 설계 (자연키 vs 대리키, “사이에 id 넣는 이유”)

### 개념

PK는 대리키(Surrogate) 권장: BIGINT AUTO_INCREMENT 또는 시간기반 UUIDv7(BINARY16).

업무 고유성은 UNIQUE로 별도 보장.

### 예시

-- 조인 테이블: id PK + UNIQUE(a_id, b_id)
meeting_participant(
  id BIGINT PK AUTO_INCREMENT,
  meeting_id BIGINT, user_id BIGINT,
  UNIQUE KEY uk_meeting_user(meeting_id, user_id)
)


### 예외/트레이드오프

다른 곳에서 이 행을 FK로 다시 참조할 일 없고, 단순 M:N 매핑이면 복합 PK로 충분.

### 주의점

InnoDB는 PK가 클러스터드 인덱스 → 단조 증가키(AUTO_INCREMENT)가 쓰기 효율↑.

### Q&A

Q: 왜 굳이 id를 또 둬?
A: 로그/알림/첨부가 이 행을 참조해야 할 때 단일 FK가 편함. 소프트 삭제/버전 관리도 쉬움.

Q: 이메일을 PK로 써도 되나?
A: 변경/충돌 위험. PK는 대리키, 이메일은 UNIQUE가 안전.

## 4) 관계 설계 (Identifying vs Non-Identifying)

### 개념

Identifying: 자식 PK에 부모 PK 포함(강 결합).

Non-Identifying: 자식은 독립 PK, 부모는 FK만(일반적).

### 예시

-- place(1) : meeting(N)  → Non-Identifying 1:N
meeting(id PK, destination_id FK → place.id)


### 예외/트레이드오프

생명주기가 완전 종속(부모 없으면 무의미)이고 함께 관리되어야 하면 Identifying 고려.

### 주의점

삭제 정책 명시: CASCADE / RESTRICT / SET NULL.

### Q&A

Q: 우리 meeting.destination_id → place는 뭔가?
A: Non-Identifying 1:N. (Identified/Unidentified 용어로는 Unidentified 1:N)

## 5) 인덱싱 전략 (MySQL InnoDB)

### 개념

외래키엔 보조 인덱스 필수.

복합 인덱스 순서: 선택도 높은 필터 → 범위/정렬 컬럼.

커버링 인덱스로 자주 읽는 쿼리 최적화.

### 예시

-- 모임별 참가자 최신순
KEY ix_part_meeting_time (meeting_id, updated_at);

-- 유저 히스토리(기간 필터)
KEY ix_hist_user_time (user_id, started_at);

-- 경로 조회(OD)
KEY ix_route_od (origin_place_id, dest_place_id);


### 예외/트레이드오프

과인덱싱 주의: 쓰기 비용/메모리↑. 핵심 쿼리 기준으로만.

주의점

함수 사용 회피: DATE(ts)=... 대신 범위 조건.

실행계획 꼭 확인(EXPLAIN).

### Q&A

Q: 단일 vs 복합 인덱스?
A: WHERE 절/ORDER BY를 덮는 복합이 더 실용적.

Q: LIKE '%키워드' 인덱스 타나?
A: 접두가 아니면 X. ngram/풀텍스트/ES 고려.

## 6) 날짜·시간 저장 & 필터

### 개념

DB 저장은 UTC, 표현은 KST 등 클라/리포트에서 변환.

인덱스 타게 범위 조건으로 질의.

### 예시

-- 월간
WHERE created_at >= '2025-09-01' AND created_at < '2025-10-01';

-- 생성 컬럼 + 인덱스
ALTER TABLE route_history
  ADD yyyymm INT GENERATED ALWAYS AS (YEAR(started_at)*100+MONTH(started_at)) STORED,
  ADD KEY ix_yyyymm(yyyymm);


### 예외/트레이드오프

CONVERT_TZ는 인덱스 못 탐. 경계값을 앱에서 계산해 전달.

### 주의점

일·주·월 집계는 경계 포함/배제(>=, <) 일관성 유지.

### Q&A

Q: YEAR(ts), MONTH(ts) 써도 돼?
A: 간단 통계용 SELECT엔 OK. 필터엔 비추천(인덱스 미활용) → 범위 조건.

## 7) 이력·스냅샷(경로 실행, 상태 변화)

### 개념

원본 로그와 가공 집계를 분리.

“그때 당시 값”은 스냅샷으로 별도 보관(모델 수정과 무관하게 재현 가능).

### 예시

route_history(
  id PK, user_id, route_id,
  started_at DATETIME, arrived_at DATETIME,
  total_time_real INT, snapshot_json JSON
)


### 예외/트레이드오프

스냅샷은 정합성 대신 재현성이 목적. 수정/정규화 대상 아님.

### 주의점

JSON은 원본 보관용. 리포팅 키는 정규 컬럼로 병행 저장.

### Q&A

Q: 스냅샷과 현재값이 다르면?
A: 의도된 것. “그때”의 기록이 목적.

## 8) 좌표/지리

### 개념

시작은 DECIMAL(10,7) 위경도.

공간검색 필요 시 생성 컬럼 POINT + SPATIAL INDEX로 확장.

### 예시

place(
  id PK, name, address,
  latitude DECIMAL(10,7) CHECK(latitude BETWEEN -90 AND 90),
  longitude DECIMAL(10,7) CHECK(longitude BETWEEN -180 AND 180),
  KEY ix_lat_lon(latitude, longitude)
);
/* 확장
ALTER TABLE place
  ADD coords POINT GENERATED ALWAYS AS (ST_SRID(POINT(longitude, latitude), 4326)) STORED,
  ADD SPATIAL INDEX sx_coords(coords);
*/


### 예외/트레이드오프

바로 POINT로 가면 문법/운영 난이도↑. 요구 나오면 하이브리드로.

### 주의점

API 응답 {lat, lng} → DB POINT는 (lng, lat) 순서.

### Q&A

Q: 네이버 지도 API 좌표 그대로 넣어도 돼?
A: DECIMAL이면 그대로. POINT면 순서만 주의(lng, lat) + SRID 4326.

## 9) 경로: 원본/즐겨찾기/히스토리 분리

### 개념

route(원본) 1건을 즐겨찾기/히스토리가 참조. 중복 제거·집계·추천 유리.

### 예시

route(
  id PK, origin_place_id, dest_place_id,
  path_hash CHAR(64) UNIQUE, total_time_plan INT, total_fatigue_plan INT,
  options_json JSON, segments_count INT
);
route_segment(route_id, seq PK, from_node_id, to_node_id, mode, time_plan, fatigue_plan);

favorite_route(id PK, user_id, route_id, UNIQUE(user_id, route_id));
route_history(id PK, user_id, route_id, started_at, arrived_at, total_time_real, snapshot_json);


### 예외/트레이드오프

정말 단순 MVP면 favorite_route/route_history에 route_json만 저장도 가능.
다만 중복·집계·추천이 어려워짐.

### 주의점

path_hash = sha256("origin|dest|n1,n2,...,nK|alpha,beta,constraints") 등 규칙 고정.

### Q&A

Q: 즐겨찾기와 히스토리가 같은 테이블이면?
A: 성격이 다름(선언적 vs 실행 기록). 분리 권장.
