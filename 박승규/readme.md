**주제**: 프론트엔드 경로 그리기 방법 학습

### 🎯 학습 목표

- 지도 API 활용법 및 경로 렌더링 기법 학습

### 📖 오늘 조사한 내용들
지도에서 경로를 그리는 방법에 대해 체계적으로 조사했다. 주요 지도 API들의 특징과 경로 렌더링 기법을 중심으로 정보를 수집했다.

#### 🗺️ 지도 API 비교 분석

| API | 장점 | 단점 |
|-----|------|------|
| **Google Maps API** | • 전 세계 데이터 커버리지가 넓고 기능이 풍부함<br>• 정확도가 높음 | • API 호출당 비용 발생<br>• 국내 상세 데이터는 제한적 |
| **Naver Maps API** | • 국내 지도 데이터 정확도가 높음<br>• 월 10만건까지 무료 제공<br>• 실시간 교통정보 연동 가능 | • 해외 지역 데이터 부족<br>• 기능이 Google Maps 대비 제한적 |
| **Kakao Maps API** | • 개발 문서가 상세함<br>• JavaScript SDK 사용 편의성<br>• 국내 POI 데이터 풍부 | • 상업적 사용 시 비용 발생<br>• 실시간 교통정보 제한적 |

#### 🛠️ 경로 그리기 핵심 기술 조사
- **Polyline**: 좌표 배열을 연결한 선분으로 경로 표현, 색상과 두께 조절 가능
- **마커(Marker)**: 출발지, 도착지, 경유지를 점으로 표시하는 기능
- **좌표 단순화**: Douglas-Peucker 알고리즘을 통해 불필요한 좌표점 제거로 성능 최적화
- **경로 애니메이션**: setInterval 대신 requestAnimationFrame 사용 권장

### 💡 수집한 정보 정리
- **데이터 구조 설계**: 경로 정보를 저장할 때 좌표 배열뿐만 아니라 메타데이터(시간, 거리, 속도 등)도 함께 관리해야 함
- **성능 최적화 방법**:
  - 좌표점 간소화
  - 화면에 보이는 영역만 렌더링하는 뷰포트 클리핑
  - 줌 레벨에 따른 디테일 조절

## 📅 2024년 9월 2일 (월요일)
**주제**: React Native vs Flutter 기술 비교 분석

### 🎯 학습 목표
- 모바일 크로스플랫폼 개발 프레임워크의 기술적 특징 파악
- 프로젝트 요구사항에 적합한 기술 스택 선택을 위한 객관적 자료 수집

### 📖 오늘의 조사 결과

#### 🔴 React Native 기술 분석

**기술적 장점:**
- JavaScript 기반으로 기존 웹 개발 지식 활용 가능
- 네이티브 컴포넌트를 브리지를 통해 호출하는 구조
- npm 생태계 활용으로 라이브러리 선택지가 풍부함
- Facebook에서 지속적으로 업데이트하며 커뮤니티 규모가 큼
- Hot Reload 기능으로 개발 생산성이 높음

**기술적 제약사항:**
- JavaScript 브리지로 인한 성능 오버헤드 존재
- 플랫폼별 네이티브 코드 작성이 필요한 경우가 있음
- Metro 번들러 의존성과 관련된 빌드 복잡성
- iOS/Android 플랫폼별 설정 차이로 인한 유지보수 부담

#### 🟣 Flutter 기술 분석

**기술적 장점:**
- Dart 언어와 자체 렌더링 엔진으로 일관된 UI/UX 구현
- Skia 그래픽 엔진 사용으로 네이티브 수준의 성능 제공
- 위젯 기반 선언적 UI로 컴포넌트 재사용성이 높음
- 플랫폼별 차이 없이 동일한 코드베이스로 개발 가능
- Ahead-of-Time 컴파일로 실행 성능 우수

**기술적 제약사항:**
- Dart 언어 학습 비용 발생
- 상대적으로 작은 커뮤니티와 제한적인 서드파티 라이브러리
- 앱 바이너리 크기가 React Native보다 큰 편
- 웹/데스크톱 지원은 아직 베타 단계

### 💡 비교 분석 결과

| 항목 | React Native | Flutter |
|------|--------------|---------|
| **성능** | JavaScript 브리지로 인한 오버헤드 | 자체 렌더링 엔진으로 우수한 성능 |
| **개발 생산성** | 기존 JavaScript 지식 활용으로 빠름 | Dart 언어 학습 비용 발생 |
| **생태계 크기** | 더 많은 라이브러리와 커뮤니티 지원 | 제한적인 서드파티 라이브러리 |
| **유지보수성** | 플랫폼별 차이로 인한 부담 | 플랫폼 간 일관성으로 유리 |

## 📅 2024년 9월 4일 (수요일)
**주제**: React Native 하이브리드 vs 순수 네이티브 앱 개발

### 🎯 학습 목표
피로도 기반 경로추천 서비스를 React Native로 개발하기 위한 기술 스택 이해 및 개발 방향 결정

**기술 스택**:
- **FE**: React Native, TypeScript  
- **BE**: Spring Boot, Kafka, Hadoop, Spark  
- **DB**: MySQL, Redis  
- **INFRA**: Ubuntu 20.04, Docker, EC2, Nginx  
- **CI/CD**: Jenkins

### 📖 오늘의 학습 내용

#### 🛠️ React Native 개발 환경 설정
- **필수 도구들**: Node.js, React Native CLI, Android Studio, Xcode
- **주요 라이브러리**: react-native-maps, geolocation, permissions, Redux Toolkit, React Navigation
- **Android Studio 터미널 사용법**: Alt + F12 단축키로 터미널 열기 및 프로젝트 실행

#### 🔄 하이브리드 앱 vs 순수 React Native 비교

**하이브리드 앱 구조**:
```
📱 React Native App (네이티브 껍데기)
├── 헤더 (네이티브)
├── 바텀 네비게이션 (네이티브) 
└── 웹뷰 → 🌐 React Web App (실제 앱 로직)
```

**순수 React Native 구조**:
```
📱 React Native App (전체가 네이티브)
├── 헤더 (네이티브)
├── 바텀 네비게이션 (네이티브)
└── 네이티브 컴포넌트들 (MapView, FlatList 등)
```

#### 🏗️ 앱 구조 설계
- **기본 네비게이션**: Home, Map, Route, Settings 탭 구조
- **프로젝트 구조**: components, screens, services, store, utils 폴더 구성
- **API 통신**: axios를 활용한 피로도 데이터 전송 및 경로 추천 요청
- **상태 관리**: Redux를 통한 전역 상태 관리로 네이티브 대비 편리한 데이터 공유

### 💡 핵심 인사이트

#### 1. **개발 방향 결정**: 순수 React Native 선택
- 피로도 측정 서비스는 **실시간 센서 데이터**와 **GPS 추적**이 핵심
- 삼성헬스 API 직접 접근 필요
- 백그라운드 위치 추적 성능이 중요
- 따라서 **순수 React Native**가 더 적합

#### 2. **하이브리드 구조의 이해**
- 네이티브 껍데기 + 웹뷰 내용물
- 웹뷰 부분만 네이티브 컴포넌트로 교체하면 순수 RN
- 앱의 전체적인 틀(헤더, 네비게이션)은 동일

#### 3. **상태 관리의 편리함**
- 네이티브 대비 전역 상태 관리가 훨씬 간편
- Redux/Context로 앱 전체에서 사용자 정보 공유
- Activity간 데이터 전달 불필요
